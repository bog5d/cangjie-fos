## BLOCKED-7 · 凭证腐烂**没有主动告警**（二轮新增 · ★ **本轮工程侧已处置**，以本节为准）

| 项 | 内容 |
|---|---|
| **现象** | 旧凭证失效到被业务撞出来，间隔约**一个月** ⇒ **腐烂周期远长于「跑一次就发现」的假设** |
| **为什么机器现在解决不了** | 通道已经备好（受控 env 注入 + 预检探针 + 稳定错误码 `DSH_AUTH_INVALID`），但**没有人/没有定时任务去探测** ⇒ 靠业务撞上才发现 |
| **影响** | 一旦腐烂，真实模型考试**当场 FAIL**（不是「静默降级」，这点是好的）⇒ 但会**卡住交付**，且**发现得晚** |
| **责任方** | 账号持有人（凭证归属）＋ 工程（探测接入） |
| **★ 本轮工程侧处置（已交付）** | 新增 `tools/dd_v1_credential_probe.py`：**开考前**即可判定「key 还在不在」，且**不做付费模型调用**（只用 `/models` 一类免费鉴权端点）⇒ 不消耗额度。<br>★ **三条硬纪律**：① **绝不输出密钥原文**（只有 sha256 指纹前 12 位，可判断「key 换没换」）；② **「没配」与「配了但坏了」分开**（`NOT_CONFIGURED` 不阻塞规则基线，`EXPIRED`/`INVALID`/`QUOTA` 才算要处理）；③ **服务端错误 ≠ 凭证坏了**（5xx/连不上 ⇒ `UNKNOWN`，**不猜**）。<br>★ **已接进一键复跑**（`tools/dd_v1_platform_selfcheck.py`：探针失败只记 advisory，**不拦停**规则基线）＋ 写进 `复跑命令.md` §0' 的**第 0 步**。 |
| **★ 残余（**仍需账号持有人**）** | **「谁来定期跑这个探针」是**组织/触发面**的事，不是代码能定的**：探针本身已在仓内，但**目前没有定时任务**在持有凭证的那台机器上跑它（Owner 已令后台任务全面停机，本仓无 cron）。⇒ 账号持有人侧需定：**谁、多久、跑在哪台机器上**。 |
| **建议做法（机器可做，等授权）** | 在 CI/定时任务里加一个**最小探针**（不跑整卷，只验「凭证可用 + 能识别模型」）⇒ 腐烂当天就红，而不是一个月后 —— ★ **代码侧已就绪，只差触发面** |
