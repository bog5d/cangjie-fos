### ★ 这批证据对应哪个 commit？（**先说清楚，免得你核错**）

| 锚点 | 是什么 | 怎么读 |
|---|---|---|
| **被测代码** | 证据里的 `git_sha` 指向的那一个提交（**代码定稿**） | `g1_pytest.json` / `门禁报告.json` / 各 `运行清单.json` 里的 `git_sha` |
| **证据入库** | 把这批证据**提交进仓库**的那一个提交（可能比被测代码晚 1 个） | `git log -1 --format=%H -- .audit/gate-runs/` |
| **交接包版本** | 本目录内容所在提交 | `git log -1 --format=%H -- docs/dd-v1-fos71/ddv1-auto-test-suite/handoff/` |

> ★ **为什么会有两个**：证据必须**先在被测代码那个提交上跑出来**（否则 `git_sha` 对不上），
> 然后**再提交进仓库** ⇒ 「跑的代码」与「入库的动作」天然是两个提交。
> ★ 判定「证据是否可信」看 **证据里的 `git_sha` + `git_dirty`**：
> **`git_dirty=false` ⇒ 测的就是那个 commit 的代码，一一对应**；
> `git_dirty=true` ⇒ 测的是**工作区**代码，**不能**对应任何 commit ⇒ 不可作为交付证据。
> ★ ★ **必须逐份读，不能看总印象**——第 3 轮独立复核就查出一处 `git_dirty=true`
>   （`.audit/gate-runs/覆盖率报告.json`：它在「改了验收项配置但还没提交」的工作区上算出）
>   ⇒ 那一份**已作废**，并在**干净树**上重生成（详见 §「第 3 轮的处置」）。
> ★ 教训：**证据必须逐份自证干净**，不能靠「这批都是干净树跑的」这种印象式断言。

### ★ 本体系**证明不了**什么（诚实边界）

独立 Reviewer 复核后点名的两处薄弱环节，**如实写在这里**，不要指望它是万能的：

1. **机器能保证「清单内的项都真跑了」，不能保证「清单没漏项」。**
   验收项清单（54 项）在 `backend/config/dd_v1_acceptance_items.v1.json`，
   它由**施工方自定** ⇒ 分母与「哪些算人工不可替代」也在施工方手里。
   ⇒ **清单本身需要业务方冻结**才算闭环；在此之前，覆盖率 98.04% 的意思是
   「**这 54 项里**机器管住了 50 项」，**不是**「全部可自动化工作里机器管住了 98%」。
2. **门禁只认「一份机读报告 + 一个 JUnit XML」。**
   报告里的 `git_sha` 可以指向任意 commit、工作区可以是脏的、报告可以由旧代码生成
   ⇒ 门禁**不会**自己校验「这份证据是不是当前这份代码产生的」。
   ⇒ 本轮已补 `git_dirty` 字段（`false` 才可信），但**校验动作仍需人来读一眼**。
   ⇒ 这正是本轮第 1 轮独立复核栽过的地方（证据出自修复前的代码），也是它被列为最薄弱一环的原因。

★ **真实 42 题的业务准确性**、**披露授权**、**Windows 真机**这三件事，
本体系**一律不装作能判** —— 见 §7 的 BLOCKED-2/3/4。

独立 Reviewer 复核发现：**第一次入库的三场考试证据，是 D4 修复（并列连接词受控拆分）之前的代码跑出来的**
（它把 `dd_v1_requirement_service.py` 回退后复跑，读数**逐项完全一致**地回到 85.43，完成了对照验证）。
⇒ **证据与代码不对应**（分数偏低 ⇒ 不是虚高，但证据链断了）。

处理：在**同一组阈值**下重跑 G1 ＋ 三场考试 ＋ 门禁 ＋ 覆盖率，并全部重新落盘。

| 考试 | 旧读数（修复前代码） | 新读数（当前代码） | 原因 |
|---|---|---|---|
| A | 96.67 | 96.67 | 不受影响 |
| **B** | **85.43**（failures=1） | **95.67**（failures=0） | D4 修复后「集团及下属公司」类**并列多义务**题不再 `INCOMPLETE` ⇒ 该题由「不完整」变「正确」 |

★ **阈值未动一个**（total≥70 / understanding=1.0 / coverage=1.0 / 42 题）—— 重跑前后逐位相同。
★ **该次（D4 重跑批次）**三场考试的运行清单均记录 `git_sha=bf709ab…` 且 **`git_dirty=false`** ⇒ 证据**严格对应**该提交的代码。

### ★ 命令行退出码口径（**别看错**）

`run --exam X` 的**退出码与门禁 `status_scored` 同语义**：
`SCORED` / `SCORED_PARTIAL` / `LOW_CONFIDENCE` ⇒ **exit=0（成功）**；`NOT_SCORABLE` ⇒ **exit≠0（失败）**。

> ★ 为什么 `LOW_CONFIDENCE` 算成功：它是**样本量不足的标注**（义务条数 < 30），**分数照给**。
> 若把 96.67 分的考试返回 exit=1，交接方会**误判为失败** ⇒ 口径统一，别自己加门槛。
