## 0. 一句话结论

**此前不是「测试不够多」，而是「测试与被测对象不是同一条链路」**：
仓内的端到端考试跑的是一条**与生产入口平行的合成链路**（夹具自带 `R1-O1` 式假义务号），
而真实考卷走的是**库侧契约 → 主体分簇 → 组包 → 阅卷**这条链路。
两套链路的**连接键（义务 ID）从未相遇** ⇒ 真实事故（91 vs 15、答卷与 Gold 对不上、
0 件交付）**在结构上不可能被现有测试发现**。

本轮把三件事补上了：
1. **考试台**（`tools/dd_v1_exam_suite.py`）：真实入口 ＋ 隔离数据面 ＋ 自动 Gold ＋ 成绩单；
2. **标准答案与系统同源**：Gold 的义务标识**从库侧权威契约导出**（不手写 ID）；
3. **门禁**：G1—G7 阈值**考试前冻结**，任何关键门槛红 ⇒ 不得宣布完成。

本轮实跑在**合成考场**上抓出 **4 个此前未发现的活缺陷**（D1/D2/D3/D4，见 §2），
其中 **D1 正是刘江 Windows 真机复测里「分数出不来」的直接根因**。

### 1.2 审计发现的**结构性**原因（三条）

1. **夹具自证（fixture self-proof）**
   `backend/tests/fixtures/dd-v1-fos71-a4|a5/gold.json` 的 `obligation_id` 写成 `R1-O1`……
   ⇒ 标准答案与生产系统**没有共享任何标识空间** ⇒ 任何「ID 对不上」类缺陷**结构性不可见**。
   ★ 本轮处置：Gold 的义务标识**从库侧权威契约导出**（`tools/dd_v1_exam_suite.py: build_gold`），
   并额外写**内容派生的稳定键** `obligation_key`（库内主键是 `uuid4`，换快照就变）。

2. **两套拆解并存（dual splitter）**
   库侧 `rq.build_obligations`（不丢题）与运行器侧 `sem.split_items`（会丢题）**长期共存**，
   各自有测试、**没有一致性测试** ⇒ P0-2 必然发生。
   ★ 本轮处置：库侧是**唯一权威**（`rq.export_obligation_contract`），运行器**消费**它；
   并加「跨入口一致性」测试（`test_dd_v1_exam_suite_l1.py::test_runner_and_library_agree_on_the_same_contract`）。

3. **「模型参与」只测到「适配器存在」**
   参与类别由**实现类**判定（这一点做得对），但**没有一次测试真的起进程、真的收响应**。
   ★ 本轮处置：第三层测试起**真进程**、核对**请求指纹**（子进程回吐的 sha256 必须等于本地算的）。

### 1.3 现有测试体系的**逐项体检**（WP0 要求逐项审计）

| 测试类别 | 现状（PR#86 head） | 评价 |
|---|---|---|
| 单元测试 | 195 个测试文件；DD-V1 相关 60+ | ✅ 覆盖广 |
| 集成测试 | 有（桥接、语义、组包各层） | ⚠️ 层内绿，**层间连接键**无测试 |
| 端到端测试 | 有（`test_dd_v1_exam_e2e.py`） | ❌ 跑的是**另一条入口**＋**预置回执** |
| 模型真实调用测试 | 有 `test_dd_v1_model_participation.py` | ⚠️ 全是**替身适配器**；无真进程 |
| Harness 接入测试 | 有（`manual` 预置回执） | ❌ `PREBAKED_RESULT` 被当成"模型参与"测试过 |
| Gold 评分测试 | 有（`test_dd_v1_exam_scoring.py`） | ⚠️ 评分函数测到位；**端到端真 Gold 跑道**缺 |

## 2. 本轮实跑抓出的 **4 个活缺陷**（此前 CI 全绿）

> 全部用**合成**材料复现，证据在 `.audit/` 与 `docs/dd-v1-fos71/ddv1-auto-test-suite/证据/`。

### D1｜多主体分簇 ID 与标准答案对不上（★ 刘江「分数出不来」的直接根因）

- **形态**：`dd_v1_bridge_service.build_semantic_obligations` 在一条义务跨多主体时把 ID 写成
  `<库侧ID>@<主体>`；而标准答案引的是**库侧那条** ID。
  ⇒ 阅卷逐题比较（`_per_obligation_rows`）按 ID 精确 join ⇒ 全落空；
  ⇒ 泄漏检测第 3 条判据（义务 ID 既不在考卷也不在 Gold）⇒ 误报 `GOLD_LEAK_DETECTED`
  ⇒ `status=NOT_SCORABLE`、`scores=null`。
- **实测**：91 条库义务 ⇒ 200 行答卷；`#108` 实测 `grade` 报 `GOLD_LEAK_DETECTED`、`scores=null`。
- **根因**：**没有「义务身份」这个概念**——分簇 ID（子视图）被当成了义务身份。
- **处置**：引入**权威 ID（库侧）**；分簇 ID 降级为子视图；阅卷按权威 ID 聚合分簇行；
  Gold 另按**内容派生的稳定键** `obligation_key` 绑定（库内主键是 `uuid4`，换快照就变）。
- **证据**：`backend/src/cangjie_fos/services/dd_v1_exam_service.py`（`authoritative_obligation_id` /
  `merge_cluster_rows` / `bind_gold_to_library`）；回归测试
  `backend/tests/test_dd_v1_exam_suite_l1.py::test_cluster_obligation_id_resolves_to_authoritative_id`、
  `..._l2.py::test_exam_b_multi_entity_obligation_is_scored_against_the_library_id`。
- **修后读数**：考试B 的多主体题（2-1，3 个分簇）由 `NO_ANSWER` 变 `CORRECT`；考试C 满分 100.0。

### D2｜题号在答卷里丢失 ⇒ 题级覆盖统计全落空

- **形态**：语义层全仓约定 `item_id` ＝ **清单题号**（`split_items`/`build_semantic_packet` 都这么写），
  但桥接层把**义务主键**塞进了 `item_id`，CLI 的 `_bridge_json` 又丢了 `text` 与题号。
  ⇒ 答卷与题号失联 ⇒ 「42 题处理了几题」读数恒为 **0**（题级覆盖全落空）。
- **实测**：`#108` 报告形态「已处理 0｜未匹配 42」；本轮修复前考试A 的
  `verifiable_coverage` ＝ **0.0**（3 题全 UNPROCESSED）。
- **处置**：桥接层按 `item_uid → item_no` 补回题号；`_bridge_json` 带上 `item_no`/`question_id`/`text`；
  `_answer_sheet_from_bridge` 用题号当 `item_id`、另带 `source_obligation_id`。
- **修后读数**：考试A `已处理 3｜正确 3｜全卷可验证覆盖率 1.0`；考试C `42/42｜覆盖率 1.0`。
- **附带修复**：模型契约里补明「`item_id` 原样照抄 packet」（否则模型会被判 `ITEM_ID_MISMATCH` 而整份被拒）。

### D3｜「实际交付件数」口径会**低报**（可能把「已交付」误判成「0 交付」）

- **形态**：答卷的**顶层**交付清单与**逐行归集**的交付件不是同一批；
  阅卷的 `delivered_files` 取二者并集（口径正确），但答卷 `summary.delivered_files` 只记归集到的部分。
  ⇒ 两个数字不一致 ⇒ 人工与机器读的是**两个口径**。
- **实测**：考试C 首轮 `summary.delivered_files=7` vs `delivered_files_attributed=46`
  （同一批交付件，两种数法）。
- **处置**：答卷 `summary` 同时给出**两个数**并写明各自含义（`delivered_files` / `delivered_files_attributed`）；
  阅卷继续以**并集**为准（事实口径）；本轮考试台把两个数都记进运行清单。
- **风险提示（未修，需业务定口径）**：「交付件数」在 HR-1（0 件 ⇒ 0 分）里是**判 0 分的依据**，
  两个口径不一致时**以哪个为准**必须冻结 ⇒ 已列入 §6 待决清单。

### D4｜并列连接词「和/及/且」未实现 ⇒ 第二类材料的要求被**静默吞掉**

- **形态**：文档承诺「按并列连接词（**且**/以及/、/**及**）切分」，实现只切「、/以及/，并且」。
  ⇒ 「请提供 X 2024 年度审计报告**和**营业执照」只切出**一条**义务（`doc_type` 取第一个）
  ⇒ **第二类材料的要求被吞** ⇒ 机器只交审计报告、营业执照没交，**且不报错**。
- **实测**：考试B 的 2-7 题 `INCOMPLETE`：期望 3 件、实交 1 件（审计报告），漏 2 件。
- **处置**：加**受控**并列拆分（`_SPLIT_RE2`）：**只有连接词两侧都能解析出材料类型才切**
  ⇒ 正常句子（「涉及」「至少」「有且仅有」）不被切碎（负例测试已锁）。
- **风险与处置口径**：这属于**行为变更**（义务条数会变）⇒ 已配负例回归；
  真实考卷上义务条数会从 91 变化 ⇒ **重跑真实考试前必须以新口径重算分母**（见 §5 BLOCKED-2）。

## 6. 给工程规范的修改建议（WP6 · 草案，未擅自发布为全局正式规范）

1. **「测试必须与生产入口同一条链路」**（新增）
   端到端测试若不走生产入口（CLI/服务），**不得计为端到端证据**。
2. **「测试夹具不得自造标识空间」**（新增）
   标准答案/夹具里的义务标识必须**从被测系统的权威契约导出**；
   自造 ID ⇒ 该测试**对 ID 类缺陷结构性免疫**。
3. **「夹具必须先验非退化」**（新增）
   造数后必须断言「题目落在互不相同的组合上」；
   本轮第一版 42 题卷因主余同源只落在 3 份材料上 ⇒ **满分是假象**（已加 `test_fixture_c_is_not_degenerate`）。
4. **「断言必须 fail-closed」**（新增）
   断言找不到输入 ⇒ **FAIL**，不得 PASS（防「假绿」）。
5. **「参与证明必须到进程级」**（修订）
   适配器存在 ≠ 模型参与；须有**进程启动 + 请求指纹 + 响应落盘**三项证据。
6. **「阈值考试前冻结」**（新增）
   门禁阈值进版本控制，附 `frozen_at`；改阈值＝换版本 + 留差异说明。
7. **「模型契约里的字段必须逐字可执行」**（修订）
   packet 里的字段语义要写进 instructions（本次补了 `item_id`＝清单题号）。

## 7. 审计的诚实边界（**本报告不证明什么**）
