## 1. 待冻结项 ①：真实 42 题 **Gold Set**

### 1.1 现状（事实）

- 仓库里的合成卷 C 是**机器自造的** 42 题考卷：题面来自 `backend/tests/fixtures/dd-v1-exam-suite/exams/C/expectations.json`，
  Gold 由机器从同一份期望文件生成（`tools/dd_v1_exam_suite.py build_gold`）⇒ **它验证的是程序，不是业务**。
- **真实 42 题清单**（Issue #108 的真实尽调清单）目前**没有业务方签字的 Gold**。
  机器只能算「与 Gold 一致率」，**算不出「Gold 本身对不对」** —— 这一条已登记为验收项 **J1（人工不可替代）**。
- HR-2 规定：Gold 未提供 / 未映射 / 未人工确认 ⇒ `status = NOT_SCORABLE` 且写明阻塞。
  ⇒ **在 Gold 冻结前，真实 42 题的成绩只能是 NOT_SCORABLE**，不是 0 分，也不是「暂按机器 Gold 算」。

### 1.2 缺什么（逐项）

| 字段 | 含义 | 为什么机器不能自己定 |
|---|---|---|
| 义务条数分母 N | 这一轮到底有多少条义务 | D4 修复（并列连接词拆分）后条数会变（见 §3.1）⇒ 分母必须**冻结在某个 commit 上** |
| 每条义务的**期望材料集合** | 该义务该交哪几件 | 「该交哪件」是业务判断（如「审计报告」要不要含正文页） |
| 每条义务的**主体** | 材料属于哪个法人 | 多主体清单里归属错 ⇒ 全盘错 |
| 每条义务的**期间** | 材料覆盖哪个年度区间 | 跨年度不顶替是硬规则 |
| **允许多件 / 必须唯一** | 允许几件、是否互斥 | 业务口径 |
| **披露级别** | 该材料可否进正式包 | 与 §2 绑定 |

### 1.3 推荐草案（供波总裁决）

**Gold Set v1 结构**（建议按此格式冻结，机器可直接消费）：

```
gold-v1.json
├─ gold_version: "ddv1-real42-gold-v1"
├─ frozen_at: <业务方签字时间>
├─ approved_by: <批准人>
├─ checklist_sha256: <真实 42 题清单的指纹>
├─ library_manifest_sha256: <材料库清单指纹>     ← 与清单一起冻结，防「题变了」
├─ obligations: [
│    { obligation_id, question_no, subject, period_from, period_to,
│      expected_files: [ {file_sha256, must_include, disclosure_level} ],
│      allow_multiple: bool, exclusive: bool,
│      confirmed_by, confirmed_at }
│  ]
└─ coverage: { obligations_total, gold_covered, coverage }
```

**冻结流程（建议）**：

1. 机器生成**候选 Gold**（规则链 + 材料库自动匹配，产出**候选**而非答案）；
2. 业务方**逐条**确认/修订（在候选上改，写明 `confirmed_by`）；
3. 机器校验：`gold_covered / obligations_total == 1.0`，**否则直接 NOT_SCORABLE**（HR-2）；
4. 冻结：`frozen_at` + 批准人 + 指纹入 config，之后**只读**；
5. 后续任何改动 ⇒ **新版本 + 新指纹**，旧版保留，**读数标「不可直接比较」**（评分规范原则第 5 条）。

### 1.4 风险（写给裁决者看）

| 风险 | 后果 | 缓解 |
|---|---|---|
| Gold 与考卷/材料库指纹不一致 | 评分落在**错卷**上，比没分更危险 | 指纹三项同冻 + HR-2 拦截 |
| Gold 由机器自动生成**未经人确认**就当答案 | 变成「机器给自己判卷」 | `confirmed_by` 必填，机器**拒收**未确认项 |
| Gold 覆盖不全（N < 义务总数） | 分数被稀释，且看不出漏了什么 | 覆盖率 < 1.0 ⇒ NOT_SCORABLE，不给分 |
| 分母在 D4 修复前后不一致 | 91 条 vs 15 条两套读数混用 | 见 §3.1 |

## 2. 待冻结项 ②：**披露分级**

### 2.1 现状（事实）

- 机器侧**已实现**安全闸，且是 **fail-closed** 的：找不到披露清单 ⇒ FAIL，绝不报 PASS（验收项 D2）。
- 受限材料不进正式包（负例，D1）；未批准不复制原件（D3）；不确定材料不混入正式包（D4）。
- 违规 5 类单列并封顶 59：错主体 / 错年度 / 受限误交 / 未批准交付 / 哈希不一致。
- **但**：合成考场用的是**考场披露口径**（`CANGJIE_DD_V1_POLICY` 覆盖），**生产策略一个字未改**；
  ⇒ **合成考场的口径不代表真实考场口径**（这在代码与文档里都写死了）。
- 哪类材料可外发，是**业务授权**（验收项 J2，不可自动化），机器自行定＝越权。

### 2.2 推荐草案（供波总裁决）：四级 + 交付规则

| 级别 | 含义 | 能否进正式交付包 | 脱敏要求 | 典型归属 |
|---|---|---|---|---|
| **L0 公开** | 已在公开渠道披露（如工商登记、公开年报摘要） | ✅ 可进 | 无 | 营业执照、公开备案 |
| **L1 内部** | 客户内部文件，但不含受限内容 | ✅ 可进（随包） | 无 | 内部台账、内部制度 |
| **L2 需脱敏** | 含敏感字段但业务上必须交付 | ⚠️ 进，但**必须脱敏** | 身份证号、账号、精确地址、个人姓名 ⇒ 掩码 | 审计报告正文、合同 |
| **L3 受限** | 法律/合规上不得外发或不得进包 | ❌ **不得进** | — | 未脱敏底稿、含个人信息的原始凭证、受限第三方材料 |

**配套规则（建议）**：

1. **默认 L2**：材料类型**未在分级表内** ⇒ 按 L2 处理（脱敏后交付），**不得**默认按 L0 放行；
2. **默认拒绝**：分级表里标 L3 的材料类型 ⇒ 任何情况下**不进包**（无论分数多高）；
3. **降级需书面授权**：把某类材料从 L3 降到 L1/L0，**必须**有书面授权记录（授权人 + 时间 + 依据），
   并写进成绩单的 `run_provenance` ⇒ **降披露要求换高分的过程是可审计的**；
4. **与评分解耦**：披露违规**独立计分**，命中即封顶 59，**不得**用高业务分抵消（评分规范原则第 3 条）。

### 2.3 风险

| 风险 | 后果 | 缓解 |
|---|---|---|
| ★ **为了让分好看而放宽披露** | 交付了本不该交的材料 ⇒ **安全事故** | 默认 L2 + L3 一律不进 + 降级必须书面授权 + 授权进 provenance |
| 分级表只覆盖部分材料类型 | 未覆盖的默认放行 ⇒ 漏披露 | 默认 L2（比默认 L0 安全） |
| 分级表按「材料名」而非「材料类型」写 | 改名即绕过 | 按**材料类型 + 实体**分级，文件名不参与判定 |
| 真实考场沿用合成考场口径 | 合成卷 PASS 不代表真实考场合规 | 分级表**必须**单独冻结一份真实版；合成版**不得**当真实版用 |

## 3. 待冻结项 ③：**业务合格线**

### 3.1 前置口径（必须先定，否则分数线没有意义）

**（a）D4 修复后的义务条数分母（BLOCKED-5）**

- 现象：本轮修了一个活缺陷 —— 并列连接词「和 / 且 / 及」未实现 ⇒ 一条题里的**第二类要求被静默吞掉**。
  修复后同一份 42 题清单**拆出的义务条数会变**。
- 影响：Issue #108 里「91 条义务」的读数，**与修复后的读数不可直接比较**（分母变了）。
- 推荐口径（建议）：
  - **主指标 = 清单题号数（42）**，稳定、跨修复不变；
  - 义务条数作为**副指标**（拆解粒度的体检数），并在成绩单里同时标注 **commit SHA**，让两套读数各自可追；
  - 真实考场的 Gold 冻结**钉在某个 SHA 上** ⇒ 分母随之固定。
- 机器不许做的事：不得拿新读数与 91 条旧读数直接对比说「变少了/变多了」；不得为让数字好看调阈值。

**（b）HR-1「0 件交付」用哪个口径（BLOCKED-6）**

- 现象：答卷 summary 同时给出 `delivered_files`（交付清单原件数）与 `delivered_files_attributed`（可归属到义务的件数），两者**可能不等**。
  （本轮实测合成卷 A：2 vs 2，**恰好相等** ⇒ 口径分歧**目前未被触发**，但真实考场可能触发。）
- 现状（**已实现的保守默认**）：阅卷**以并集为准**（不会漏判「有交付」）⇒ 已实现的保守默认，但**不是**冻结口径。
- 推荐口径（建议）：**并集**（`delivered_files ∪ delivered_files_attributed`）。
  - 理由：HR-1 的目的是「**没交东西就别装作考好了**」⇒ 判 0 分的条件应是「**一件都没交**」；
    可归属数只反映**归因**，归因失败不该把「交了 3 件」判成「0 件」。
  - 但要同时**单列**两个数，避免用归因口径掩盖归因缺陷。

### 3.2 推荐草案：硬红线 + 三档分数线

**（A）硬红线（任一不满足 ⇒ **不论总分多少，一律不通过**）**

| 编号 | 硬红线 | 判定来源 |
|---|---|---|
| **BL-1** | 安全闸 **PASS**，违规数 **= 0** | 成绩单 `safety_gate`（5 类违规单列 + 封顶 59） |
| **BL-2** | **42 题全部进入处理链路**，`questions_processed == 42`，`verifiable_coverage == 1.0` | 成绩单 `exam_coverage` |
| **BL-3** | **Gold 覆盖率 = 1.0**（缺一条 ⇒ NOT_SCORABLE，而不是低分） | HR-2 + Gold 冻结件 |
| **BL-4** | 交付件 **SHA256 逐件复算一致**，无哈希不一致 | 验收项 E2 + 安全闸 HASH_MISMATCH |
| **BL-5** | **零错主体交付、零错年度交付** | 安全闸 WRONG_ENTITY / WRONG_PERIOD |
| **BL-6** | **无受限材料误交**（L3 一律不进包） | 安全闸 RESTRICTED_DELIVERED |
| **BL-7** | **未批准交付 = 0** | 安全闸 UNAPPROVED_DELIVERY |

**（B）三档分数线（对**总分**）—— 推荐草案**

| 档 | 总分 | 含义 |
|---|---|---|
| **合格** | **≥ 85** | 达到「可交付给人工终验」的水平 |
| **观察** | 70 ≤ 分 < 85 | 有可交付物，但有明确缺口；**不得**进入正式验收流程 |
| **不合格** | < 70 | 不得交付 |

**（C）为什么不是 70 / 不是 100**

- **不是 70**：现有 G4 的 70 是**合成卷**线，而合成卷 C 实得 **100.0**、A 卷规则基线 **96.67**
  ⇒ 70 分线在合成卷上**形同虚设**，照搬到真实 42 题等于没设线。真实卷的题面更杂（多主体、跨年、多文件、缺失材料），
  按合成卷读数外推，真实卷落在 85—95 区间的可能性最大 ⇒ **85 是「比合成卷低、比及格高」的折中**。
- **不是 100**：真实 42 题存在**合法的不确定性**（材料缺失、主体未登记、多文件不全）；
  100 分线等价于「不允许一道题有缺口」，会把**如实弃答**也判成失败 ⇒ 逼迫系统**瞎猜**（更危险）。

**（D）必须与「AI 成绩方差」一起裁决的口径**

★ **实测（且说法改过两次，以本节为准）**：
- 第 3 轮复核时曾据「干净树 17 次恒 96.67」**撤回**「不可复现」；
- **2026-10-31 干净树重跑实测推翻该撤回**：commit `0b1ec84`（`git_dirty=false`）dsh ⇒ **77.5**；
  commit `a1fb96b`（同卷同模型、同样干净树）⇒ **96.67 × 4 次**。
⇒ **最终**：**AI 成绩存在方差**（96.67 / 77.5 两档，**干净树上都出现过**）；
「只有脏工作区才不稳」这个解释**不成立**（脏树读数只是**不可作交付证据**，不是波动的原因）。
⇒ 但**分布仍未在受控条件下测出**（温度/提示词版本未钉死）⇒ 单次分数**仍不足以**作为验收依据
（理由是「没测过分布」，不是「已测出噪声很大」）。
⇒ ★ 这也是**必须由业务方拍板**的原因：「取几次、什么统计量、要不要阈值带」是**验收口径**，机器不能替业务定。

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **单次**（现状） | 跑 1 次，用这 1 次的分数 | 便宜、快 | 方差**未测量** ⇒ 不可靠 |
| **N 次取中位数**（**推荐**） | 同卷跑 **3 次**，取中位数 | 抗单次抖动；成本 = 3× | 成本 3 倍；仍需固定温度/提示词版本 |
| **多次取分布 + 阈值带** | 跑 3 次，判「中位数达标且最差不低于 X」 | 最接近真实交付风险 | 判据复杂，需波总拍板 |

> ★ **推荐 N=3 取中位数**，并要求成绩单**同屏列出 3 次分数**（不只给中位数）⇒ 让业务方看得见方差。
> ★ 同时建议**锁死温度与提示词版本**（本轮已记 `prompt_version`，但**温度未固定** ⇒ 方差来源之一）。

**（E）合格线适用到哪个分数 —— 必须显式声明**

本轮成绩单**已分列**：`RULE_BASELINE_SCORE`（规则基线分）vs `AI_SYSTEM_SCORE`（AI 系统分）vs `NOT_SCORED`。

- 建议：**业务合格线**只对 **AI 系统分**（即真实模型参与下的系统成绩）设线；
- **规则基线分**作为**对照系**报告，**不设合格线**（它不是交付物）；
- 模型缺席时 AI 成绩 = `NOT_SCORED` ⇒ **不得**用规则基线分顶替、**不得**写 0。

### 3.3 风险（写给裁决者看）

| 风险 | 后果 | 缓解 |
|---|---|---|
| ★ **事后改线**（看完成绩再调阈值） | 破坏「阈值先于结果」纪律，评分失去意义 | 冻结写入 config + `frozen_at` + 指纹；改线必须**换版本 + 留差异说明**（沿用 A1—A3 的做法） |
| 只对**单次**成绩判线 | 方差未测量 ⇒ 结论没有置信区间 | N=3 取中位数 + 同屏列 3 次分数 |
