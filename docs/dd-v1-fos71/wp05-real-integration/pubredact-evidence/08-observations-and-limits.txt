## O-3 材料库代号侧的 7 个文件 · **已逐件回退到 HEAD**（Gate-2 ③）
  事实：材料库代号是**英文词**。第一轮用「**子串**即命中」口径，
  把**英文单词内的子串**误判成命中 ⇒ 7 个文件被改，产生了中英混排的
  **标识符污染**（形如 `seen_in<替身>s`）。
  ★ 司仓**独立复现**：用正确词边界 `(?<![A-Za-z0-9_])code(?![A-Za-z0-9_])`
    复扫 master ⇒ **命中 0 文件 / 0 处** ⇒ 那 7 个文件的改动是**零收益 churn**。
    ★ 本包**独立复现**了旧口径的数字：**7 文件 / 17 处**（纯子串），
      同一棵树在词边界口径下 **0 文件 / 0 处** ⇒ 旧数字确系**扫描器假阳性**。
  处置：7 个文件**逐件回退到 HEAD**（SHA256 与 HEAD **逐件相等**已验）——
    4 个产品源码 + 2 个后端用例 + 1 个前端组件。
  ⇒ 改后**产品源码侧**只剩 `tools/` 下 2 个文件的**文档串 / argparse help 文本**
    字面量改动 ⇒ **零行为变化**（见 PUBREDACT-NOTE.md 第 5 节第 3 条）。
  ★ 扫描器已同步补上**代号词边界规则**；**真实名保持子串规则**
    （中文没有词边界 —— 这正是短名也必须命中的原因）。

## O-6 Gate-2 收口时**本包自己新发现**的两个问题（已修，已登记）
  ① **marker 注释语法用错 ⇒ 前端构建失败**：Gate-2 第二轮追加的 marker 行在
    `frontend/src/components/DueDiligenceWizard.tsx` 里用了 **Python 风格**的 `#` 注释
    ⇒ **硬语法错误**，`npm test` / `npm run build` 直接失败（esbuild 解析报错）；
    在 `CHANGELOG.md` 里同样用 `#` ⇒ **渲染成 H1 标题**（污染公开仓文档）。
    ⇒ 已按**文件类型**改成正确语法（`//` / `<!-- -->`），**只改注释、不改任何行为**；
      改后前端 `npm test` / `npm run build` **均退出码 0**（见 03-frontend-checks.txt）。
    ★ 教训：marker 必须**按扩展名选注释语法**，且**必须实跑该语言的工具链**验证。
  ② **真实材料库里该短名的出现次数：双方口径不同，已对账（不是矛盾）**：
    - 口径A（司仓）：`cd ~/dd-v1-realbase && grep -ro "$P8" --include="*.txt" --include="*.md" . | wc -l`
      ⇒ **88,297 次**（`$P8` = 权威模式文件第 8 行；本包**不携带任何字面量**）；
    - 口径B1（执行者，`grep -ro` 全文件类型）⇒ **231,497 次**；
    - 口径B2（`LC_ALL=C grep -ro` 全文件类型，二进制也逐行计）⇒ **231,593 次**；
    - 口径C（逐字节全量计数，含二进制、decode=ignore）⇒ **316,906 次**
      （另一个 2 字形态 **55,947 次**）；
    - 文件数：`grep -rIl` ⇒ **362** 个；`LC_ALL=C grep -rl` ⇒ **458** 个。
    - ★ 差异机制已定位：**文件类型范围**（仅 .txt/.md vs 全部）+ **二进制文件里的出现次数**
      （`grep -o` 对二进制只输出 1 行 vs 逐字节逐次计数）
      ⇒ 各数**各自可复现、不是互相矛盾**，写明口径即可。
    - ★ **该数字对 Gate-2 ② 的裁决不承重**：裁决依据是「该形态是**真实客户标识**、
      且散落公开仓 25 处 / 12 文件」，**不依赖具体计数**；无论按哪个口径，
      该形态在真实材料库中都是**大量出现**（远超任何假阳性量级）
      ⇒ 仍是**真实客户短名、不是假阳性** ⇒ 「采纳清除」的裁决**不受影响**。
