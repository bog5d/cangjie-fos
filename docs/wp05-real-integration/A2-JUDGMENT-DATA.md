## 0. 一句话目标与验收口径

**目标**：把 A1 接上之后仍然「判不出来」的那几根线补齐 —— 让判定层拿到
**规范材料类型、敏感等级、权威主体、期间、清单边界**，从而把
「判不出来」拆成**能判的结论**（MATCHED / RESTRICTED / MISSING / CONFLICT / UNCERTAIN），
而不是一律 UNCERTAIN。

**验收口径**：任务书第 5 段 **A2-1 … A2-16 + A2-6b**，共 **17 条**。
司仓自检 **17/17 PASS**（`a2-evidence/acceptance-selfcheck.txt`），
但**自检不算验收** —— 独立 Reviewer 必须自己复算（HG-07）。

1. **CONFLICT 284 → 82 → 0**：284 条假冲突来自**跨法人混桶**（A1 已修）；

### 2.6 ★ F1 的**产品侧守卫**（`alias_kind`）—— 名单侧修了还不够

★ **独立监工第 36 轮指出的缺口，司仓独立复核后成立**：
别名表原先只有三条守卫（「别名非空」「`source_ref` 非空」「主体必须已登记」
「别名不得跨主体复用」）—— **没有一条**能挡住

⇒ F1 只修在**名单侧**（生成器不登记分类目录）⇒ **换个材料库、换个人写脚本、
或将来任何一次程序化登记**，都会把「同一分类目录下不同子型的材料进同一桶
⇒ 异哈希 ⇒ 报假 CONFLICT」原样复现。

**修法（司仓采纳监工建议 (b)，并加严）**：

| # | 机制 | 落点 |
|---|---|---|
| 1 | **别名叫种类** `alias_kind`：`LEGAL`（法定全称/工商简称/名录英文简称，**主体维度**）/ `USCI`（统一社会信用代码，**主体维度**，跨库稳定键）/ `DIRECTORY`（**材料分类目录**，**分类维度，不是主体维度**）；表结构加列 + 旧库 `ALTER TABLE` 迁移 | `dd_v1_entity_service.py` |
| 2 | **形态硬守卫**：别名形如「数字编号 + 分隔符」（`1.xxx` / `10.xxx`）⇒ 只能是 `DIRECTORY`；**形态判定优先于声明** ⇒ 显式声明成 `LEGAL`/`USCI` ⇒ **拒绝登记**（不静默改写） | `register_entity_alias()` |
| 3 | **DIRECTORY 型不参与主体归一**：`alias_map(include_directory=False)`（默认）⇒ 分类目录型别名**既不算 `entity_ok`，也不参与冲突分桶** ⇒ 落「主体未登记」桶 ⇒ **不产生假 CONFLICT**，同时**照常留痕** | `dd_v1_match_service._alias_map_for()` |
| 4 | **回归锁 4 条**：形态判定正确 / 显式登记成法定别名被拒 / 登记了也不参与归一 / **产不出 CONFLICT 但仍留痕** | `tests/test_dd_v1_alias.py`（15 → **19** 条） |

### 2.7 ★ 判定口径的**覆盖边界**（披露；不改判定）

> ★ 本节回答「MATCHED / PARTIAL 这些数字**覆盖了哪些义务、没覆盖哪些**」——
> 口径必须说清，**不得**让读者把「某个档位有数字」误读成「全库都判对了」。

1. **`doc_type` 未被认出的义务 ⇒ 类型维度**没有门槛**。
   `need_type` 会退化为 `max(1, 主体数 × 年数)`，且无类型约束时不拦候选
   ⇒ `doctype_cov = 1.0` 是**「无门槛放行」，不是「类型已认定」**。
   ⇒ 这类义务的 `doctype_cov` **不可**读作类型证据。
2. ★ **MATCHED 目前只覆盖 `doc_type` 被认出的义务类型**。
   实测：三条 MATCHED 的 `doc_type` 均已识别；类型未识别的义务**未产出 MATCHED**。
3. **职责类要求（如「组织架构」）在类型词表里无对应项** ⇒ **不硬归一**。
   把它强行映射成某个材料类型属于**编造** ⇒ **不修，改为如实披露**：
   该类义务的缺口按**主体维度**报（示例：指名主体名下确无该类材料 ⇒
   唯一候选属于**另一登记主体**且**不可交付** ⇒ 判 **PARTIAL（主体缺 1/1 家）**，
   ★ **这个判定是正确的**，不是缺陷）。
4. **主体维度**：`need_entities` 恒为**非空洞** ⇒ 主体维度**始终是真实门槛**
   （不存在「无主体要求 ⇒ 无门槛放行」的空洞满分）。
   案例B/C 因清单项**没有「<主体>：」前缀** ⇒ `entity_scope` 恒空 ⇒ 主体维度**不可判定**
   ⇒ MATCHED 只可能在案例A 产出（见 §2.3 / §2.5）。

> ★ **不要把 §2.7 读成「判定不准」**：它是**覆盖范围的声明**——
> 哪些义务能被哪一维判、哪些**物理上判不了**，都必须写在交付面上。
